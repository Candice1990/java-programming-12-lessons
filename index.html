JDK, JRE and JVM

The Java Development Kit, or JDK, is the toolkit used to develop Java software. It includes javac for compilation, java for launching programs, debugging and documentation tools, and the runtime components required by those tools.

The Java Runtime Environment, or JRE, provides what a Java program needs to run: the JVM, standard libraries and supporting runtime components. The JDK includes these runtime components as well as development tools such as javac; a runtime alone does not provide that compiler.

The Java Virtual Machine, or JVM, is the abstract execution environment for class files. The standard library is the collection of reusable APIs—such as String, Scanner, List, Files, and Thread—that applications call instead of rebuilding common facilities.

RememberSelect a JDK for the project, not merely an editor. Without a configured JDK, the IDE has no compiler or Java platform against which to check the program.

03

Java data types: Primitive and Reference

Java variables come in two kinds. A primitive variable holds the value itself: after int x = 10;, x stores 10. A reference variable holds a reference to an object: after String s = new String("hi");, s holds a reference to that String object — or it could hold null, meaning "no object." Think of a reference as a way to locate an object on the heap, rather than an address you can inspect or manipulate in Java.

Assigning a primitive copies the value, while assigning a reference copies the reference. Two references to the same mutable object see changes made to that object through either reference. String objects are immutable, so use the array example in the next part to see shared changes.

A reference type and its input sources

Scanner is a class, so Scanner is a reference type. In Scanner input = new Scanner(System.in), input holds a reference to a Scanner object; it does not hold the text or an integer. The object reads text from a source and its methods return values such as int, double, boolean or String.

Choose the source when constructing the Scanner. Choose what to read when calling a method. A token is one piece of text separated by a delimiter; Scanner uses whitespace by default. Method Overloading

Overloading lets several methods share one name when their parameter lists are different. Start with what a method receives and what it returns, then compare the calls.

One name, different parameter lists

In int max(int x, int y), int before max is the return type; x and y are parameters. In max(10, 15), 10 and 15 are arguments. return sends the result back to the caller.

Overloaded methods have the same name but different parameter types, numbers of parameters, or orders of types. Changing only a parameter name or the return type does not create a new overload.

For these ordinary calls, the compiler chooses an overload from the declared argument types. The helpers below are static so main can call them without first creating an object.

Object-Oriented Programming

Object-oriented programming organizes a program around objects, combining state (fields) with behavior (methods). Start with the four principles—abstraction, encapsulation, inheritance and polymorphism—then explore classes, constructors and objects through code.

The four OOP principles

Abstraction exposes the useful operations without making the caller manage the internal steps. A television offers turnOn(); its user does not need to operate the circuitry.

Encapsulation keeps related data and methods together and controls access to the data. A private volume field can be changed through a method that checks the allowed range.

Inheritance lets a more specific class build on a more general class. Television extends Device means a television is a kind of device.

Polymorphism lets the same operation use different implementations. A Device reference can call turnOn(), and a Television object can supply the television-specific behavior.

Overloading is often called compile-time polymorphism. Overriding uses the actual object at runtime. Keep these two selection rules separate; later lessons develop overriding and inheritance in detail.

Class, object and reference

A class defines a type. An object is an instance of that class. A reference variable identifies an object: in Circle first = new Circle(), Circle is the type, first is the variable, and new Circle() creates an object.

To design a class, ask: what does it store, and what can it do? A Circle stores radius and calculates area and perimeter. Fields describe state; methods describe behavior.

Each object has its own instance fields. An instance method such as first.area() uses the radius of first’s object. The first examples use public fields so you can see this relationship; data hiding follows.

Choose fields first, then methods that use those fields. A method calculating a result should normally return it; main can decide how to display it.

Use double for dimensions and int for whole-number marks. Use boolean for a yes/no question such as isSquare(). A Student grade can return a char such as A or B.

Constructors and constructor overloading

A constructor runs when an object is created. It has the class name and no return type, not even void. new Rectangle(4, 3) creates an object and invokes the matching constructor.

A no-argument constructor receives no values; a parameterized constructor receives values. Constructors can be overloaded using different parameter lists, just like methods.

Java supplies a default no-argument constructor only when a class declares no constructor. If you write Rectangle(double length, double breadth), new Rectangle() needs an explicitly declared no-argument constructor.

In this.length = length, this.length is the current object’s field and length is the parameter. this(...) calls another constructor in the same class; in Java 21 it must be the first constructor statement.

Polymorphism

A parent-type variable can refer to a child object. In Animal pet = new Dog(), Animal is the variable’s declared type, while Dog is the actual object’s type. No extra Animal object is created.

The declared type determines which methods you may call through the variable. The actual object determines which overridden instance-method body runs. Therefore pet.speak() runs Dog.speak(). This runtime choice is called dynamic method dispatch.

The useful result: one loop can call speak() on different Animal objects. Each object supplies its own behavior, so the loop needs no separate test for Dog or Cat.

Abstract classes and abstract methods

An abstract class is a base class that cannot be instantiated directly. An abstract method declares an operation without a body. A concrete child class must implement the abstract methods it inherits.

Every shape should have an area, but there is no single formula for all shapes. Shape declares area(); Rectangle and Circle provide their own formulas.

An abstract class can also contain fields, constructors and ordinary methods with bodies. Here describe() is shared, while its call to area() uses the actual shape’s implementation. You can write Shape s = new Circle(2), but not new Shape().

Optional reference: additional inheritance rules
  • super.method() calls the inherited parent implementation. super(...) calls a parent constructor; constructors are not inherited or overridden.
  • A final method cannot be overridden. A private parent method is not inherited as an overridable method.
  • Static methods are hidden, not dynamically overridden. Field access also depends on the declared reference type.
  • An override cannot reduce accessibility. A reference return type may be more specific, and checked exceptions cannot be broadened beyond the parent declaration.
  • Assigning a child object to a parent reference is upcasting. Downcasting requires a compatible actual object or it fails at runtime; use polymorphic methods when possible.

An interface describes a capability

An interface declares a contract that different classes can implement. A class extends at most one class but may implement several interfaces. A variable of an interface type can refer to any object implementing it, allowing the caller to depend on the capability rather than the implementation.

Ordinary interface abstract methods are public, so their class implementations must be public. Interface fields are public static final constants, not per-object state. Interfaces may also have default and static methods; private helper methods support interface implementations. A default method provides behavior, but does not give the interface ordinary instance fields.

02

Abstract class or interface?

Use an abstract class when related types share state, construction rules and partial implementation. Use an interface to express a role that otherwise unrelated classes can adopt. A class can combine both: extend a shared base and implement several capabilities.

If unrelated interfaces provide conflicting defaults with the same signature, the implementing class must resolve the conflict explicitly. Java’s multiple interface inheritance does not mean that it inherits multiple independent parent-class object states.

05

A static nested class is namespaced inside its enclosing class but has no implicit outer object. It can directly use only static members unless a reference to an outer object is passed explicitly. Choose this form when nesting improves organization but instance capture is unnecessary.

06

Local and anonymous classes

A local class is declared inside a block, usually a method, and is visible only there. An anonymous class defines and instantiates a one-off subclass or interface implementation in one expression. Both may capture local variables only when those variables are final or effectively final.

Anonymous classes remain useful when a one-off implementation needs fields, several methods, or special initialization. When a functional interface needs only a short behavior, a lambda is usually clearer.

Project structure and packages

02

Packages and access boundaries

Packages create namespaces and establish an access boundary. public is visible everywhere; protected is visible in the package and to subclasses under Java's inheritance rules; package-private is visible only within the package; private is visible only within the declaring top-level class and its nested types.

Package names conventionally use a reversed domain, such as ca.school.registration. The package declaration, directory structure, imports, compiler output, and classpath must agree. Packages are therefore part of a program's architecture, not merely labels at the top of files.

A package is tested across files

05

Compile-time, logical, and runtime failures

A compile-time error prevents class files from being produced; examples include malformed syntax, an unknown name, or an incompatible type. A logical error compiles and runs but produces the wrong result because the algorithm or formula is incorrect. A runtime failure occurs while the program is executing; many, but not all, runtime failures are represented by exceptions.

RememberClassify the failure before choosing a remedy: compiler diagnostics, tests and debugging, or exception handling.
06

The exception hierarchy

Throwable has two major branches. Error represents serious JVM or environment failures that applications normally do not recover from. Exception represents conditions application code may handle. Checked exceptions must be caught or declared; RuntimeException and its subclasses are unchecked.

Checked versus unchecked is a compiler rule, not a measure of severity. A checked exception is appropriate when callers can reasonably anticipate and recover from the condition. An unchecked exception commonly reports a violated precondition, invalid state, or programming mistake.

RememberChoose an exception type according to the API contract and the caller's recovery options, not simply according to how alarming the failure feels.

01

Lifecycle and scheduling

A Thread begins in NEW, becomes RUNNABLE after start(), may enter BLOCKED, WAITING, or TIMED_WAITING, and ends in TERMINATED. RUNNABLE includes both ready-to-run and currently-running states from the JVM's perspective.

Scheduling order is not guaranteed. Priority and yield are hints, not correctness mechanisms. sleep pauses the current thread until the requested duration elapses unless it is interrupted; scheduling may delay the actual resumption. The method does not release intrinsic locks already held.

RememberIf a program is correct only when one thread happens to run first, the program is not correctly synchronized.
02

Completion, interruption, and daemon threads

join() waits for another thread to terminate and establishes visibility of its completed work. Interruption is a cooperative cancellation request. Blocking methods often respond by throwing InterruptedException; code should stop, propagate the exception, or restore the interrupted status rather than silently swallowing it.

A daemon thread does not keep the JVM alive after all user threads finish. Set daemon status before start(). Daemons are suitable for background assistance, not for work whose final write or cleanup must be guaranteed.

03

Start workers together; wait for all results

A group of workers can be stored in a Thread array before collections have been introduced. Start every worker in one loop, then join every worker in a second loop. Joining immediately after each start would serialize those tasks and prevent the intended overlap.

A ThreadGroup can associate named platform threads for organizational purposes, but it does not make shared data safe or replace explicit completion. Priority and yield are scheduling hints, not ordering rules. Never use a guessed sleep duration as proof that another task has completed.

04

Race conditions and critical sections

An operation such as value++ is a read-modify-write sequence rather than one indivisible action. Two threads can read the same old value and lose one update.

The critical section is the complete region that reads or changes a shared invariant. Protecting only one statement is insufficient when the rule spans a check followed by an update.

05

One monitor must protect one protocol

synchronized acquires an object's intrinsic monitor. Only code using the same monitor participates in the same mutual-exclusion rule. Locking different objects does not protect shared state.

An ATM check-and-withdraw sequence is one transaction. If checking and withdrawal are synchronized separately, another customer may enter between them. The monitor must cover the complete transaction.

RememberState the invariant in one sentence, then verify that every read and write participating in it uses the same lock.

Class objects are runtime type descriptions

02

Built-in annotations communicate intent

@Override asks the compiler to verify that a method actually overrides or implements an inherited declaration. @Deprecated marks an API that callers should avoid and may provide migration guidance. @SuppressWarnings narrows a deliberate compiler-warning suppression to a selected declaration.

03

Annotations are metadata, not behavior

An annotation type is declared with @interface. Its elements look like parameterless methods and may have default values. Applying an annotation records metadata; nothing happens unless the compiler, a tool, or runtime code reads and acts on it.

@Target limits where the annotation may appear. @Retention chooses whether it exists only in source, in the class file, or at runtime. Reflection can read only annotations retained at runtime.

04

Discovering and invoking marked methods

A framework-like program can scan methods, request a particular annotation, validate its values, and invoke the method. Reflective invocation wraps a failure thrown by the target method, so production code must unwrap and report the underlying cause carefully.

05

Trade-offs and boundaries

Reflection reduces direct coupling and supports extensible tools, but names and signatures may fail only at runtime. Private-access overrides weaken encapsulation and may be restricted by Java modules. Reflective code is also harder to navigate and test.

Prefer normal interfaces, constructors, and method calls for application logic. Use reflection at infrastructure boundaries where dynamic discovery provides clear value, then validate early and convert failures into meaningful domain errors.

A direct call such as service.greet() is checked by the compiler against a known type. Looking up getMethod("greet") depends on a string and can fail at runtime if the name or parameter signature is wrong. Method.invoke may also wrap an exception thrown by the invoked method.

The cost and optimizations of reflection depend on the operation and runtime. Do not assume one fixed slowdown factor. Prefer a normal interface for routine application behavior; use reflection where runtime discovery is the purpose. Access checks and module boundaries still apply.

01

Generic classes and methods

A type parameter is a placeholder chosen when the generic type is used. Box<String> and Box<Integer> share one implementation but expose different compile-time APIs. The diamond operator asks the compiler to infer constructor type arguments.

A generic method declares its own type parameter before its return type. Its type parameter is independent of any type parameter declared by the surrounding class.

02

Invariance and bounded type parameters

Even though Integer extends Number, List<Integer> is not a subtype of List<Number>. If it were, a caller could add a Double to a list that promises to contain only Integer values. Generic types are therefore invariant by default.

A bounded parameter such as <T extends Number> restricts acceptable types and makes Number operations available inside the implementation. Multiple bounds are written with one class bound first, followed by interface bounds.

03

Type parameters belong to declarations

A class-level T is available throughout the instance API of Box<T>. A static method cannot refer to that instance type parameter unless it declares an independent parameter of its own. A generic method places <T> before its return type, for example static <T> T echo(T value).

Use descriptive type names when they improve clarity, such as Key and Value. Generic type arguments must be reference types; use Integer rather than int. Autoboxing can convert primitive values at API boundaries, but unboxing a null wrapper throws NullPointerException.

Type erasure and restrictions

Java implements most generics through type erasure. Type arguments guide compilation but are usually not reified as distinct runtime classes. Consequently, code cannot directly create new T(), new T[], test instanceof List<String>, or use primitives such as List<int>.

Raw types such as List bypass generic checking for compatibility with older Java code. They should not be used in new code because they move errors from compilation to runtime.

06

Generic inheritance preserves its declared type

A generic class or interface can be extended or implemented just like a non-generic type. ArrayList<E> implements List<E>, and List<E> extends Collection<E>; the same E is carried through the relationship. A specialized subclass may either keep a parameter open or fix it to one concrete type.

This does not make Box<Integer> a subtype of Box<Number>. Those are two parameterizations of the same generic class and remain invariant. When an API needs a family of related parameterizations, bounded wildcards express that relationship.

Erasure does not mean all type information disappears

A type parameter generally erases to Object or its leftmost bound. The compiler inserts casts where necessary and may generate bridge methods so overriding continues to work after erasure. Different parameterizations such as Box<String> and Box<Integer> ordinarily share one runtime class.

Generic signatures may still be recorded as metadata and inspected through reflection. Two overloads whose signatures become identical after erasure are illegal. A static field belongs to the erased class, not separately to each type argument.

08

Collections organize groups of values

A collection framework separates contracts from storage strategies. List promises sequence and positional access; Set promises no duplicates under its equality rule; Queue describes processing order. Map associates keys with values and is part of the framework, but does not extend Collection.

Declare a variable using the smallest interface that expresses the operations needed. List<String> names the contract while new ArrayList<>() selects storage. Generics preserve the element type through add, get and iteration, reducing casts and catching mismatched values at compilation.

09

Choose by required behavior before performance

Ask whether duplicates are allowed, whether positions matter, whether keys identify values, and whether processing order is required. Then choose an implementation. A linked structure is not automatically faster merely because insertion is mentioned: locating an insertion point also costs time.

The next lessons study operations and implementation trade-offs in detail. For now, read List<E> extends Collection<E> extends Iterable<E> as a type relationship that carries the same element parameter forward. This is interface inheritance, separate from invariance between List<Integer> and List<Number>.

Collection defines common operations

Collection<E> defines operations such as add, remove, contains, size, isEmpty and clear. Bulk operations include addAll, removeAll and retainAll. These are contracts: some implementations do not support every mutation, and optional operations may throw UnsupportedOperationException.

contains and remove(Object) use equality rather than reference identity. List adds positional access, permits duplicate values and defines equality in terms of the same elements in the same order. Set is a different contract and does not gain indexed get simply because it is a collection.

02

ArrayList is a resizable array

ArrayList stores references in an internal array and resizes that storage as needed. get(index) gives constant-time indexed access. Appending is amortized constant time, while inserting or removing near the beginning requires shifting later elements. Size is the number of stored elements; capacity is an internal storage allocation.

remove(1) on a List<Integer> removes the element at index 1. remove(Integer.valueOf(1)) removes the first equal value. This is an important overload distinction. Index bounds run from zero through size - 1 for reading existing elements.

The enhanced for statement is built on Iterable and Iterator. An iterator supplies hasNext(), next(), and sometimes remove(). It separates traversal from the internal representation of the collection.

Implementing Iterable and Iterator

An enhanced for loop over an Iterable is syntactic convenience for obtaining and using such an iterator. Arrays are also supported by enhanced for through a separate language translation.

A fresh iterator should represent an independent traversal. next() must throw NoSuchElementException when exhausted, not return an arbitrary null sentinel. Iterator.remove(), when supported, removes the last element returned by next(); it cannot be called twice without another next().

Queue and Deque describe processing order

Queue offers add/remove/element methods that can throw on failure and offer/poll/peek alternatives that signal ordinary failure with a special return value. poll and peek return null for an empty queue, which is one reason implementations such as ArrayDeque forbid null elements.

Deque supports both ends. addLast and removeFirst implement a FIFO queue; push and pop use the front for a LIFO stack. ArrayDeque is a useful general starting point for stack or queue behavior when null elements and concurrent access are not required.

08

A PriorityQueue is not a sorted list

PriorityQueue chooses its head by priority, using natural order or an explicit comparator. poll repeatedly removes the smallest remaining element under that ordering. Ties need not preserve insertion order. Iterating or printing the queue does not promise sorted order.

Queue priority does not mean operating-system thread priority. One is an ordering rule for stored elements, the other is a scheduling hint. Keep the concepts separate. For sorted output from a priority queue, deliberately poll until it is empty or copy its elements and sort the copy.

Map contracts and traversal

05

Insertion order, access order, and bounded caches

LinkedHashMap's three-argument constructor can enable access order, where successful access moves an entry toward the end. Combining access order with removeEldestEntry supports a bounded least-recently-used policy.

Without accessOrder=true, the same removal hook evicts according to insertion order instead. The constructor choice is therefore part of the data structure's behavior.

RememberDo not infer an ordering contract from one printed HashMap result; only documented contracts are portable.
06

Map keys are unique; values need not be

put(key, value) inserts an association or replaces the value for an equal key. get(key) returns the associated value or null if none is mapped; in maps permitting null values, containsKey distinguishes absence from a present null mapping. remove(key) deletes the association.

keySet(), values() and entrySet() are backed views, not independent snapshots. Removing through a supported view removes the corresponding mapping. Traverse entrySet when both key and value are needed. A Map is not directly Iterable, but its views are collections that can be traversed.

07

Choose lookup and order independently

HashMap provides no iteration-order guarantee. LinkedHashMap preserves insertion order by default and can optionally maintain access order. TreeMap stores keys in comparison order and supports sorted-range operations. Null handling differs between implementations; do not assume that all Map implementations accept a null key.

Expected constant-time hash lookup assumes a suitable hash distribution. TreeMap operations such as get and put are logarithmic in entry count. These performance models help choose a starting point; actual workload and memory behavior still matter.

Specialized and legacy utilities

Hashtable and Enumeration are legacy APIs. StringTokenizer is also a legacy tokenizer. Existing programs may require them, but new designs normally choose HashMap or ConcurrentHashMap, collection views or Iterator, and split, Scanner, or a deliberate parser according to the problem.

02

Arrays and Collections are utility classes

Arrays contains static helpers for arrays, including sorting, searching, copying and comparison. Collections contains static algorithms and wrappers for collection objects. Collection is the element-container interface; Collections is a different plural-named utility class.

Arrays.sort changes an array in place. Collections.sort(list) and list.sort(comparator) change a mutable list in place. Binary search requires data sorted under the same ordering used by the search. Comparator supplies an external ordering strategy

Comparator<T> declares compare(left, right), allowing a caller to choose an order without changing the element class. Comparator.comparingInt and comparing extract a sort key; reversed reverses an order and thenComparing resolves ties. Comparable defines one natural order; Comparator can express many alternatives.

Apply reversed at the intended level. comparingInt(score).reversed().thenComparing(name) sorts by descending score and ascending name. Reversing the entire composed comparator would reverse both rules. A tie-breaker makes output deterministic when primary values match.

Functional interfaces give lambdas a type

05

Predicates combine with and, or and negate. Functions compose with andThen or compose, whose execution orders differ. A Supplier can delay an expensive fallback until it is required. Creating a lambda usually does not perform the action; calling its interface method does.

06

A stream is a pipeline, not a container

A stream does not store elements. It connects a source to zero or more intermediate operations and one terminal operation. filter, map, distinct, and sorted are intermediate; collect, reduce, count, forEach, and findFirst are terminal.

Intermediate operations are lazy. They perform no traversal until a terminal operation requests a result. This allows the implementation to combine operations and stop early for short-circuiting terminals.

07

Intermediate operations describe a new stream

filter keeps elements matching a predicate. map transforms each element. flatMap flattens a stream of streams. distinct removes duplicates according to equality; sorted orders elements; limit bounds the result. These operations return streams rather than immediately producing a final container.

A pipeline usually pulls each element through the necessary operations instead of completing a full separate traversal for every stage. Stateful operations such as sorted may need to buffer data. A terminal operation can short-circuit: anyMatch may stop at the first match, but sorting before it can still require consuming all input.

08

Choose the terminal result deliberately

count produces a number; anyMatch and allMatch produce booleans; findFirst produces an Optional because no result may exist. collect accumulates results, and reduce combines values with an operation such as addition. For numeric data, mapToInt followed by sum or average avoids repeatedly boxing primitive values.

Stream.toList() produces an unmodifiable list in the Java 21 examples. If later mutation is required, collect with Collectors.toCollection(ArrayList::new). Do not assume Collectors.toList() guarantees a specific mutable implementation. Optional.orElseGet uses a Supplier only when the result is absent.

09

Purity, reuse, and parallelism

A stream is single-use; after a terminal operation, create a new stream for another traversal. Intermediate operations should avoid shared side effects because they make reasoning difficult and may break under parallel execution.

parallelStream() is not an automatic speed switch. Parallel work has coordination costs and requires associative operations, sufficient data, suitable tasks, and measurement. Begin with a correct sequential pipeline and optimize only from evidence.

10

Performance follows the work, not the syntax

A sequential stream can be clear without being faster than a loop. Parallel pipelines need enough independent work to outweigh splitting and coordination. Reduction operations must be associative and have suitable identity values. Side effects on an ordinary shared ArrayList are unsafe in a parallel forEach.

Prefer a collector that manages the reduction rather than external mutation. Encounter order and execution order are different: parallel forEach does not promise encounter-order output, while forEachOrdered preserves it where defined. Measure a representative workload before choosing parallel execution.
